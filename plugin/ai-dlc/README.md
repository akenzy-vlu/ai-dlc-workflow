# ai-dlc (plugin)

The agent-facing half of AI-DLC. The skills under `skills/` hold the workflow and the gate
controller; this plugin holds the five subagents that do the work inside those gates and the
two hooks that stop an agent from stepping around them.

It exists for the same reason `aidlc.py` does. CLAUDE.md already states these rules —
never hand-edit the three generated files, never set `current_gate` directly, `history.jsonl`
is append-only, `verified_by` is a human's signature. Stating them is not enforcing them. An
agent reads "do not hand-edit `.aidlc-state.yaml`", agrees sincerely, and edits it anyway when
a gate check is in the way, because that reasoning is locally plausible every single time. So
the rules move from prose into a program that refuses.

## Install

```bash
/plugin marketplace add /path/to/ai-dlc      # this repo — it carries .claude-plugin/marketplace.json
/plugin install ai-dlc@ai-dlc
```

`aidlc-implementer` and `aidlc-tester` previously lived loose in `~/.claude/agents/`. Delete
those two files after installing — the plugin ships the same two names, and leaving both is a
duplicate definition:

```bash
rm -f ~/.claude/agents/aidlc-implementer.md ~/.claude/agents/aidlc-tester.md
```

## The agents

Each one is defined as much by what it refuses to do as by what it does. Every refusal below
is a separation of duties that the method depends on.

| Agent | Does | Will not |
|---|---|---|
| `aidlc-explorer` | Phase 0 inventory into `.ai/architecture.md`, splitting discoverable facts from questions only a human can answer | write `verified_by:` — that signature is a human's, and `check_g0` trusts it |
| `aidlc-implementer` | One ticket, end to end, code plus tests, stopping at `submit` | touch a file outside `touches:`, or `accept` its own work |
| `aidlc-tester` | **Writes** the tests that prove a ticket's `verifies:` criteria | change production code to make a test pass |
| `aidlc-test-runner` | **Runs** a suite and maps results back to AC ids | change anything at all, or tick a done-when box |
| `aidlc-security-reviewer` | Reviews one ticket's diff for security defects, rejects with a recorded reason | run `accept`, or fix what it finds |

`aidlc-tester` and `aidlc-test-runner` are the pair most easily confused: the tester *authors*
tests and may edit test files; the runner *measures* and writes nothing.

## The hooks

Both are `PreToolUse`, both refuse with `permissionDecision: "deny"`, and both **always exit
0** — a matched rule denies, an internal error allows and says so. That asymmetry is
deliberate and matches `verify.py`'s `skipped` rung: a guard that fails loudly on ordinary
work gets switched off, and a switched-off guard is worse than an absent one.

### `block-dangerous`

*Generic destruction* — `rm -rf` aimed at `/`, `~`, `$HOME`, `.` or `*`; `sudo rm`; a force
push over `main`; `git clean -fdx` (which deletes `.env` and `.ai/credentials.env`, since
neither is in git); `dd` to a device; `mkfs`; a fork bomb; piping a download into a shell.

*Controller integrity* — the part that makes this AI-DLC's rather than generic:

| Refused | Why |
|---|---|
| Writing `.aidlc-state.yaml` | a view folded from `history.jsonl`; editing it makes the file and the record disagree. Use `aidlc pass` / `reopen` / `reconcile`. |
| Writing `05-ticket-graph.md`, `06-traceability.md`, `.ai/**/registry.yaml` | regenerated by `uowg --write` so they cannot drift from the tickets |
| Rewriting `history.jsonl` — `>`, `sed -i`, `truncate`, `rm`, `mv` | append-only; its `merge=union` strategy assumes nothing rewrites it |
| Adding `verified_by:` to `architecture.md` | the human trust boundary for G0 |

Reached through an editor tool or through the shell, both are covered.

### `no-secrets`

1. **Bash command strings** — inline `export *_TOKEN=…`, `Authorization: Bearer …`,
   `--password=…`, a URL with embedded credentials.
2. **Write/Edit content** — vendor key shapes (Anthropic, AWS, GitHub, Stripe, Slack, Google),
   private-key blocks, and a filtered catch-all for hardcoded assignments.
3. **Reading credential files** — `.env`, `.ai/credentials.env`, `.ai/.auth/`, `*.pem`,
   `id_rsa*`, `~/.aws/credentials`, via `Read` or via `cat`/`head`/`xxd`. `.ai/credentials.env`
   is listed explicitly because a `.env*` gitignore pattern does not match it.
4. **git** — staging a credential file, committing with one in the index, or pushing commits
   that touch one.
5. **Sending the file elsewhere** — `curl -d @.env`, `curl -T`, `wget --post-file=`,
   `scp`/`rsync` of a credential file (`secret-upload`), and `cp`/`mv` of one to a path the
   other rules no longer recognise (`secret-copy`). Neither the transcript nor the index ever
   sees these, so coverages 3 and 4 both miss them; an upload is as final as a push.
6. **Printing a live credential** — `gcloud auth print-access-token`, `aws configure get
   *secret*`, `aws secretsmanager get-secret-value`, `kubectl get secret -o yaml`, `op read`,
   `vault kv get`, `security find-generic-password`, `heroku config`, `gh auth token`,
   `git credential fill` (`credential-command`); and whole-environment dumps — bare `env` or
   `printenv`, `printenv <NAME_THAT_LOOKS_SECRET>`, `export -p` (`env-dump`). No secret file is
   involved: the value arrives from a keychain, a cloud API or the process environment.

The precision line for the last two is drawn at what actually reaches the transcript.
`kubectl get secret <name>` with no output flag lists names and is allowed; add `-o yaml` and
it is refused. `cp .env .env.bak` stays inside the credential world and is allowed;
`cp .env /tmp/x` is not. `env | grep -v TOKEN` pipes the dump to another program rather than
to the transcript, so only a bare `env` that *is* the whole command is refused.

Writing *into* `.env` or `.ai/credentials.env` is allowed on purpose: they are the designated
home for a real credential, and refusing there would push it into source instead. Those files
are protected on the read side and at git.

Denial reasons never echo the matched secret back — a reason is transcript too.

## Wrapped commands: `rtk` and friends

Every rule below dispatches on the program a command invokes, so a wrapper that renames it
disables the rule. [`rtk`](https://github.com/rtk-ai/rtk) — the token-filtering CLI proxy the
AI-DLC skills recommend — is the case that matters in practice, because it ships a PreToolUse
hook of its own that *rewrites* commands: on a machine with rtk installed, `git push` becomes
`rtk git push` without anyone choosing it.

`rules.head_of` therefore strips an `rtk` prefix the same way it strips `sudo` and `env`, and
resolves the subcommand to the program whose rules apply:

| written | policed as |
| --- | --- |
| `rtk git add <path>` | `git add <path>` |
| `rtk read <path>` | `cat <path>` — a file dumper |
| `rtk proxy rm -rf /`, `rtk err …`, `rtk summary …` | the command they wrap |
| `rtk run -c '<command>'` | the shell string inside, scanned as its own segment |
| `rtk gain`, `rtk config` | nothing — rtk's own commands run no other program |

Adding a wrapper to `RTK_WRAPPERS` or `RTK_ALIASES` in `rules.py` extends this; a wrapper
that is neither is treated as rtk's own command and policed no further. `rtk run -c` nesting
is followed to `RTK_NEST_CEILING` levels, because a hook the user is waiting on must
terminate.

## When a hook is wrong

Detection is heuristic, so assume it will occasionally be wrong and fix it in config rather
than by disabling the plugin. Create `.claude/aidlc-hooks.json` in the project:

```json
{
  "allow_paths":    ["fixtures/**", "test/data/*.pem"],
  "allow_patterns": ["EXAMPLE_ONLY_[A-Z]+"],
  "disabled_rules": ["no-secrets/git-push-secret"]
}
```

`allow_paths` adds to the defaults (`*.example`, `*.sample`, `*.template`, `*.dist`);
`allow_patterns` are regexes tested against the scanned text; `disabled_rules` takes the rule
ids printed in every denial. `AIDLC_HOOKS_OFF=1` silences everything for one command — for a
genuine one-off, not as a habit.

## Development

Stdlib-only Python 3, like everything under `skills/`. No build.

```bash
pnpm skills:check     # py_compile every script, hooks included
pnpm hooks:test       # 39 cases: every rule fires, and stays quiet next door
```

The tests drive the hooks as subprocesses over stdin, exactly as Claude Code does, because the
wire protocol *is* the contract. Both halves are asserted: that each rule catches the thing it
exists to catch, and — the half that decides whether anyone keeps the plugin enabled — that it
does not catch the neighbouring command that is fine.
