# T-04-01 — block / unblock, carrying the state the block interrupted

## Context

`blocked` is already a legal status in `VALID_STATUS` (`uow_graph.py:40`) and already a
legal source state for `in_progress` in `ALLOWED_FROM` (`aidlc.py:953`) — but no subcommand
ever sets it, so the only way to reach it is to hand-edit a ticket, which is the move
`SKILL.md` calls theatre, and the wait leaves no trace. Per ADR-06 the block event carries
the state it interrupted, so unblocking restores rather than guesses.

## Implementation notes

- `ALLOWED_FROM` gains `"blocked": {"todo", "in_progress", "review"}`.
- The block event records `from` — the status at the moment of blocking — plus the required
  reason and actor.
- `unblock` is not an `ALLOWED_FROM` target: it reads the last unpaired block event for the
  ticket and restores its `from`. **Refuse when there is no matching block event** — a
  hand-edited `status: blocked` has none, and refusing is the intended pressure toward the
  controller.
- `cmd_ready` already skips anything whose status is not `todo`, so a blocked ticket drops
  out with no change there; confirm rather than assume, and confirm dependents of a blocked
  ticket stay blocked too.
- Reuse `_transition`'s existing structure and lock; `block` needs no checklist check —
  blocking is not progress and must never be gated behind done-when boxes.

## Done when

- [x] `block` sets the status, requires a reason, and records the interrupted state
- [x] `unblock` restores `in_progress` from `in_progress`, and `review` from `review`
- [x] `unblock` on a ticket with no block event is refused
- [x] `aidlc ready` omits blocked tickets; their dependents stay blocked
- [x] `python3 -m py_compile` clean
