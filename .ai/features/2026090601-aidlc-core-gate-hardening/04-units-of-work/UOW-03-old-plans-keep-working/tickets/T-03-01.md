# T-03-01 — Stamp the tool's RULESET into .aidlc-state.yaml at init

## Context

A-12 is the rejected assumption that made this ticket necessary: `check_ruleset` only
returns warning strings, and the pin it reads lives in `.ai/aidlc.yaml` — one value shared
by every feature in the repo, including plans already closed. Bumping it would apply new
rules retroactively, which A-01 forbids. ADR-03 puts the pin on the plan instead.

## Implementation notes

- `cmd_init` writes `ruleset: <RULESET>` into the state dict. Read `RULESET` from
  `uow_graph` through the existing import, never a second literal — two copies of a version
  number is how they diverge.
- `load_state` returns the stamp; **absent means 4.** Every plan that exists anywhere today
  has no stamp, so the default is the compatibility guarantee, not a fallback.
- The repo-level pin in `.ai/aidlc.yaml` keeps its current advisory meaning and is not
  merged with this one. Mildly redundant, and much safer than making one imply the other.
- `save_state` must round-trip the new key; confirm `reconcile` preserves it, since it
  rebuilds the view from the trail and the stamp is not a trail event.

## Done when

- [x] A newly initialised feature's state file carries `ruleset: 5`
- [x] A state file with no stamp reads as ruleset 4
- [x] `reconcile` preserves the stamp rather than dropping it
- [x] The value comes from `uow_graph.RULESET`, not a second literal
- [x] `python3 -m py_compile` clean
