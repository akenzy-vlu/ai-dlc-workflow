# T-04-03 — The reply composer, and its honest disabled state

## Context
AC-02 is mostly about what the UI does when it *cannot* do the thing. Four reasons a reply
is impossible, and each one should read as a fact about this run rather than as a
mysterious grey box.

## Implementation notes
- Read `canReply` and `cannotReplyReason` from the thread. Do not re-derive either — the
  rule lives in `reply()` and the UI would drift from it
- Disabled: show the reason as helper text under the box, and an "Launch a fresh run"
  action beside it
- The composer sends `acknowledged: true` — the same acknowledgement the launch modal makes
  explicit. If the user has not seen that acknowledgement in this session, show it once
  before the first reply rather than sending it silently
- Enter sends, Shift+Enter newlines. Disable the send button while a reply is in flight
- Cap at 4000 characters to match the DTO, with the count shown near the limit

## Amendment during construction
Nothing in the original `touches` actually mounted this component anywhere — three files
that compile and are never rendered are not a feature. Added one line to
`agent-run-drawer.tsx`, beside the `<AgentThread>` it already renders as `children`, since
that container already resolves `repositoryId`/`slug`/`ticketId` for the thread.

"Launch a fresh run instead" links to the ticket's own page
(`ROUTES.feature(repositoryId, slug)?ticket=ticketId`) rather than opening
`LaunchAgentModal` inline: that modal requires `ticketTitle`, which nothing this composer
has access to carries, and fetching it solely for this button would be a new query this
ticket's scope does not otherwise need. The ticket page already hosts the full launch flow
this same link pattern is used for it in `agent-runs-page.view.tsx`, unrelated to this
feature.
