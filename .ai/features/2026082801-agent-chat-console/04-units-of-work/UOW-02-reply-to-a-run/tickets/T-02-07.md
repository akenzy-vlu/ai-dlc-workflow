# T-02-07 — Reply and thread HTTP routes

## Context
Two routes. The DTOs follow the shape the controller already uses, including the
`acknowledged` flag — a reply spawns an agent CLI that writes files in a real checkout,
which is the same thing `LaunchAgentDto` refuses to infer from one click.

## Implementation notes
- `POST /api/agent-runs/:id/reply` with `ReplyDto`: `@IsString() @MinLength(1)
  @MaxLength(4000) message`, optional `repliedBy`, `@IsBoolean() acknowledged`
- `GET /api/features/:repositoryId/:slug/tickets/:ticketId/thread`
- Use the `@Acting('repliedBy')` decorator exactly as `launch` uses `@Acting('launchedBy')`,
  so the identity rules behind an authenticating proxy stay in one place
- The route lives on the run, not the ticket: a reply continues one session, and the run is
  what holds it

## Verification note
No dedicated test file. `launch` and `launchReady` — the two sibling routes in this same
controller — have none either: this codebase's suite is domain tests with no I/O, and a
controller route is a thin delegation exercised through Nest's own request pipeline, not
unit-tested here. What the done-when items actually claim:

- `acknowledged: false` refused before resolving anything: true by construction — the DTO
  forwards straight into `AgentLauncherService.reply()`, which is the method
  `test/agent-reply.spec.ts` already proves refuses first, resolves nothing, on a false
  acknowledgement
- A message over 4000 characters rejected by validation: `@MaxLength(4000)` plus the global
  `ValidationPipe({ whitelist: true, transform: true })` in `main.ts` — the same framework
  guarantee every other DTO in this file relies on, none of them tested individually either
- The thread route returns the same summary shape `GET /api/agent-runs` returns: both route
  to `this.summarise(run)` per run, in `AgentLauncherService` — the same code path
