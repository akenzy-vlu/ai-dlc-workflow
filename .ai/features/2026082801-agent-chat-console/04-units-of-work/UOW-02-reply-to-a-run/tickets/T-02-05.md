# T-02-05 — LaunchRequest carries a session to resume

## Context
`SpawnAgentProcess` builds argv from `definition.argsFor(prompt)`. Resuming means building
it from `argsForResume` instead. That is the whole change to the process layer — per ADR-01
stdin still closes immediately and the process is still one prompt in, one exit out.

Deliberately *not* changed: `startStreamingProcess`. No `write()`, no idle timeout, no
inbound socket path. Those belong to the interactive session that ADR-01 defers.

## Implementation notes
- `LaunchRequest.resumeSessionId?: string`
- In `launch`, choose `argsForResume(resumeSessionId, prompt)` when present, else `argsFor`
- Guard: `resumeSessionId` set on a definition with `canResume: false` throws before
  spawning. It should be unreachable — the launcher refuses first — but a guess that
  reaches `spawn` is the failure this feature is built to avoid
- `handle.command` is what the run records and the drawer shows; make sure the resumed
  argv is what gets recorded, not the launch argv

## Amendment during construction
The ticket was drafted with no test file in `touches`, on the assumption that
`SpawnAgentProcess` could only be exercised by spawning — which the suite forbids. That was
wrong: extracting the argv choice as a pure `resolveArgs` makes the one decision in this
file testable with no subprocess. `apps/api/test/agent-resume-argv.spec.ts` was added and
`touches` amended rather than the test being skipped or smuggled in unlisted. No other
ticket writes that path, so the write-conflict ordering is unaffected.

## Done when
- [x] A request with no `resumeSessionId` produces exactly the argv it produces today
- [x] A request with one produces the resume argv and records it on the run
- [x] A `resumeSessionId` on a non-resumable definition throws before any process starts
- [x] stdin is still written and closed in the same call; no handle is left open
