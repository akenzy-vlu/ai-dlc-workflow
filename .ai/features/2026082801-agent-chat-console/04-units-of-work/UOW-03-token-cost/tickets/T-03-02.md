# T-03-02 — Translator reads usage from the result event

## Context
The `isResult` branch already pulls `total_cost_usd`, `num_turns` and `duration_ms`. The
`usage` object sits beside them and is dropped.

A-05 is still pending on the exact key names. Read defensively: an unexpected shape leaves
the counts null, which is the same outcome as a CLI that never reports them, and neither is
an error.

## Implementation notes
- Read `event.usage` as a record; take `input_tokens`, `output_tokens`,
  `cache_read_input_tokens`, `cache_creation_input_tokens`
- Guard each with `typeof === 'number'` the way the surrounding code guards `total_cost_usd`
- Do not add the counts to the one-line `result` transcript string. That line is the human
  summary — turns, seconds, dollars — and four more numbers would bury it. The counts go to
  telemetry only
- Keep the `isResult` detection as it is: identified by keys as well as by `type`, so a
  renamed type does not lose the cost summary

## Amendment during construction
The done-when items here are assertions, and the draft listed no spec — the plan put the
usage tests in T-03-03. But T-03-03 asserts against the *recorded* transcript and resolves
A-05; the shape cases (a wrong type, a non-object `usage`, the transcript line unchanged)
belong with the code that handles them. Added as `stream-json-usage.spec.ts`, a separate
file from the `stream-json.spec.ts` that T-01-02 and T-03-03 share, so no ordering changes.
Weakening the done-when to make it tickable was the alternative, and it is the move this
whole apparatus exists to prevent.
