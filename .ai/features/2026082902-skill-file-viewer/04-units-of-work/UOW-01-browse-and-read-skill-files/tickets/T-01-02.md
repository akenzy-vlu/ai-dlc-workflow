# T-01-02 — SkillFiles use case

## Context

The controller (T-01-03) needs a skill id resolved to a `sourcePath` before either of
T-01-01's functions can run — that resolution is what `SkillInventory.list()` already
does via `SkillCatalogPort.find(id)`. This ticket is the thin application-layer seam
between "an id came in over HTTP" and "here are `listPackageFiles`/`readPackageFile`
called against the right root", exactly the shape `SkillInventory` already models for the
existing list endpoint.

## Implementation notes

- `SkillFiles.listFiles(id)`: `catalog.find(id)` → not found throws (maps to 404 in
  T-01-03); found → `listPackageFiles(skill.sourcePath)`, mapped to whatever shape
  T-01-03's DTO needs (flat, sorted — no tree-building here, that's presentation-side per
  `03-logical-design.md`).
- `SkillFiles.readFile(id, relativePath)`: same id resolution, then
  `readPackageFile(skill.sourcePath, relativePath)` from T-01-01. Let `RefusedError` and
  any not-found error propagate untouched — T-01-03 owns the HTTP status mapping.
- Constructor-inject `SkillCatalogPort`, same as `SkillInventory` already does — no new
  port needed.
- Register the new use case as a provider in `skills.module.ts`, alongside the existing
  `SkillInventory`/`InstallSkill` providers.

## Done when

- [x] `listFiles` on an unknown id throws the same not-found shape `SkillInventory` uses
      elsewhere in this context, so T-01-03 can map it consistently
- [x] `readFile` on an unknown id throws the same way
- [x] `readFile` on a known id delegates to `readPackageFile` with the skill's actual
      `sourcePath` — proven with a fake `SkillCatalogPort`, no real filesystem needed
- [x] `pnpm --filter @aidlc-console/api typecheck` passes
