# T-01-03 — GET /api/skills/:id/files and /files/content routes + DTOs

## Context

Wires `SkillFiles` (T-01-02) onto two new routes on the existing
`@Controller('api/skills')`, per the Contracts section of `03-logical-design.md`. `path`
is a query parameter on the content route, not a route segment — a segment would swallow
the `/` inside `references/methodology.md`, the same reasoning
`portfolio.controller.ts`'s own `?path=` parameter already applies.

## Implementation notes

- `GET /api/skills/:id/files` → `SkillFiles.listFiles(id)`, mapped to
  `SkillFileNodeView[]` (`relativePath`, `name`, `isDirectory`, `extension`, `size`).
  404 on unknown id.
- `GET /api/skills/:id/files/content?path=<relativePath>` → `SkillFiles.readFile(id, path)`,
  mapped to `SkillFileContentView` (`relativePath`, `content`, `encoding`, `truncated`,
  `size`). Map a caught `RefusedError` to `400`; map not-found to `404`.
- New DTOs go in `skill-file.dto.ts`, following `skill.dto.ts`'s existing style
  (`class-validator`/`class-transformer` where the file already uses them for
  `InstallSkillDto`).
- No change to `GET /api/skills` or `POST /api/skills/:id/install` — this ticket is
  additive only.

## Done when

- [x] `GET /api/skills/:id/files` on a fixture skill (a temp-dir package, per
      `skill-installer.spec.ts`'s pattern — real fs on purpose, not a mocked one) returns
      its file list, excluding every `IGNORED` path (AC-01)
- [x] `GET /api/skills/:id/files` on an unknown id returns `404`
- [x] `GET .../files/content?path=SKILL.md` returns that file's content
- [x] `GET .../files/content?path=../../../etc/passwd` (or any other escaping value)
      returns `400`, not file content
- [x] `pnpm --filter @aidlc-console/api test` passes

## Correction applied in review

The implementer correctly flagged that `SkillFileNodeView.size` (required by
`03-logical-design.md`'s Domain model table, and already typed as required `size: number`
on the web `SkillFileNode` entity from T-01-04) was unobtainable from T-01-02's
`SkillFileEntry`, which carried only `relativePath` — a real gap spanning T-01-02's
`touches:`, not something this ticket could fix within its own declared scope. Fixed by
extending `listPackageFiles()`'s `PackageFile` (`skill-digest.ts`) and `SkillFiles.listFiles`
(`skill-files.use-case.ts`) to carry `size` from the same `fs.stat` `readPackageFile` already
performs elsewhere — one stat call per file, additive to both functions' existing consumers
(`filesystem-skill-installer.ts`, `filesystem-skill-catalog.ts`), no behavior change for
them. Verified: `pnpm --filter @aidlc-console/api test` (182/182) and `typecheck` both pass
after the fix; `skill-files.use-case.spec.ts` and `skills.controller.spec.ts` updated to
assert the real `size` values.

A second gap the implementer also flagged, from the same review: `03-logical-design.md`'s
error taxonomy (line 69) requires "file missing (e.g. deleted between list and read)" to
surface as `404`, but `readPackageFile`'s `fs.realpath` catch-all wrapped *any* resolution
failure — including plain ENOENT for a file that was simply never there — into
`RefusedError`, which this ticket's own controller maps to `400`. Fixed in `skill-digest.ts`
by checking `(cause as NodeJS.ErrnoException).code === 'ENOENT'` and throwing `NotFoundError`
in that case specifically; every other `realpath` failure (unresolvable symlink, permission
error) still throws `RefusedError`, unchanged. This does not touch the `../`/absolute-path
guard, which runs before `realpath` and is unaffected. Added a unit test in
`skill-files.spec.ts` and a controller-level test in `skills.controller.spec.ts`; full suite
now 184/184.
